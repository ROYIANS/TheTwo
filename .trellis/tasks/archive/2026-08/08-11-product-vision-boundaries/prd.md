# 择途产品前景、目标与边界讨论

## Goal

在正式开发前，从项目发起者本人的真实求职处境出发，明确择途第一阶段服务的目标用户、首要问题、核心价值、最小闭环和明确边界，最终形成可以约束后续产品设计、原型和开发的产品边界说明。讨论不以罗列功能为目标，而以确认“帮助谁在什么处境下完成什么以前很难完成的结果”为目标。

## What I already know

* 项目发起者是 2020 年毕业、具备 Java、全栈和前端经历的工程师，职业重心逐渐转向前端，并承担过前端架构职责。
* 当前公司经营不善并已欠薪，发起者准备重新进入求职市场；与三年前相比，个人经历更丰富，但就业环境更差，AI 也正在改变岗位数量、岗位要求和求职方式。
* 发起者会主动、灵活地使用 AI，并希望先为自己打造一个真正参与求职全过程的工具，而不是做一个脱离真实需求的展示项目。
* 最初需求来自具体行动：筛选有用职位、优化或生成简历、生成打招呼内容、鉴别职位与公司、准备申请，并在求职结果出现后复盘策略。
* 已有产品定义将择途描述为“开源、可信、以求职者为中心的 AI 求职与职业决策平台”，但目标用户、首要问题和 MVP 边界仍未冻结。
* 旧讨论已经形成职业档案、职位导入、可解释匹配、申请材料、求职 CRM、面试准备、漏斗诊断等能力地图；这些是方向池，不等于第一版范围。
* 当前长期闭环是“认识自己 -> 发现机会 -> 判断是否适合 -> 准备并执行申请 -> 记录结果 -> 调整策略”。
* 第一版面向中文用户；不为了国际化牺牲中文招聘平台、沟通方式和求职习惯的适配。

## Assumptions (temporary)

* “性价比高”不是固定的岗位属性，而应由机会真实性、风险、回报、投入、个人匹配和长期职业影响共同构成；具体优先级仍需确认。
* 赞助可能成为项目长期维护资金来源，但具体渠道、治理和可持续性尚未决定。

## Deferred Questions

以下问题不改变当前产品入口与 MVP 闭环，留给后续独立任务处理：

* 不提供官方 SaaS 的前提下，长期如何让非技术求职者低门槛使用。
* 机会判断的具体维度、数据来源、硬门槛、权重和表达模板如何设计。

## Expansion Sweep

以下内容用于检验产品边界和避免返工，不自动进入 MVP。

### Future evolution

* 从软件工程师扩展到其他中文职业时，需要逐个验证职业语言、能力证据、招聘渠道和风险信号，不能假设软件行业模型天然通用。
* 不提供官方 SaaS 的前提下，需要为非技术用户探索桌面化、一键部署或可信第三方部署等低门槛路径，但不能改变用户数据控制原则。
* 开源项目需要形成不依赖闭源功能墙的维护、治理和赞助机制。

### Related scenarios

* 项目文档、代码平台、作品集、绩效材料等可以成为职业证据来源，但择途只负责导入、整理和用于职业决策，不替代原始工作工具。
* 招聘平台、公司信息源和模型提供商应通过可替换的连接能力接入，不能成为产品中心。
* 学习、作品建设和个人品牌只有在服务明确职业目标时进入范围，不扩张为独立教育或内容运营平台。

### Failure and edge cases

* 网络来源可能过期、被操纵或互相引用，提供来源不等于事实已经得到证明。
* AI 可能根据早期错误画像不断强化后续判断，用户纠正、反例和不确定性必须能够打断反馈循环。
* 自部署会带来升级、备份、安全配置和本地数据丢失风险，未来需要给用户可理解的保护路径。
* 外部模型和数据源可能停服、涨价或改变政策，核心职业画像和历史记录不能被供应商锁定。

## Confirmed MVP User Flow

第一版主路径由两个连续价值阶段组成：

```text
用户提供基本信息、现有简历与职业材料
  -> Agent 主动追问并建立初步职业画像
  -> 用户确认和纠正画像
  -> 生成或完善一份适合更新到招聘平台的基础简历
  -> 用户通过浏览器插件、截图、文本或链接采集职位
  -> 职位可以来自招聘平台、社区、公众号、公司官网、朋友或其他渠道
  -> 结合职业画像推荐和排序机会
  -> 深挖职位与公司信息
  -> 给出明确但非强制的行动建议，并展示来源、风险、匹配、机会成本和未知项
  -> 用户决定是否值得投入
  -> 对值得申请的岗位生成基于事实的定制材料与沟通草稿
  -> 用户审核并亲自在招聘平台沟通或投递
```

首次完成画像和基础简历是准备阶段的价值时刻；持续采集、判断真实职位并把值得申请的机会准备到可以行动，是第一版反复使用的核心价值循环。

### Why each MVP stage is required

* 职业画像与基础简历建立个人事实、目标和限制的共同底座，否则职位判断无法真正个性化，申请材料也容易编造或相互矛盾。
* 来源无关的职位采集让用户能把现实中遇到的具体机会带入系统，否则产品只能讨论抽象职业建议。
* 标准化、联网调查和证据整理用于补齐职位信息、识别风险与未知项，否则系统只是复述 JD。
* 明确但非强制的行动建议把证据转化为可执行判断，否则用户仍需独自完成最困难的综合分析。
* 完整申请决策包把“值得申请”的判断推进到“可以行动”，形成第一版可观察的结果，而不是停留在分析报告。
* 自动平台聚合、求职 CRM、面试准备和结果反馈都有后续价值，但不是达到第一版“申请就绪”的必要条件。

## Requirements

* 产品讨论必须从真实用户处境和预期结果出发，再推导功能，不从页面或功能数量出发。
* 择途的核心产品承诺是提高用户的职业决策质量与掌控感：帮助用户获得更完整的证据、理解取舍、明确下一步，并从真实结果中修正策略。
* 节省时间、增加有效面试和获得更合适的 Offer 是重要收益与观察指标，但产品不承诺其无法独立控制的求职结果。
* 择途的长期产品中心是用户持续演化的职业画像与决策记录；职位数据、生成材料和 AI 模型围绕这份长期职业上下文工作。
* AI 是建立和理解职业画像的主要方式：从用户提供的材料与对话中整理经历和能力，主动发现信息缺口，并结合后续真实结果更新理解。
* 职业画像是用户拥有、可以检查和纠正的个人职业模型，不是平台为营销、筛选或操控用户而建立的隐藏标签集合。
* AI 主动提取、追问、总结并提出对用户的理解；用户拥有职业画像的最终解释权。
* 用户职业事实、AI 推断和仍未知的信息必须保持可区分；AI 推断不能静默覆盖用户已经确认或明确表达的内容。
* 用户可以确认、否认和修正 AI 提出的画像；发生冲突时，系统应保留依据和变更记录，而不是暗中选择一个版本。
* AI 扮演批判性的职业顾问：不仅执行用户设定的目标，还要理解目标动机，并结合职业画像、市场证据、现实限制和机会成本检验目标。
* 当目标存在明显风险、自相矛盾或替代路径时，AI 应明确提出质疑和备选方案；它不能为了迎合用户而隐藏不利判断，也不能替用户作最终决定。
* 所有重要职业判断采用证据优先原则，明确区分可验证事实、AI 推断和依赖用户偏好的价值判断。
* 外部事实应尽可能给出来源与时间，职业画像事实应能追溯到用户材料或确认记录，AI 推断应说明依据和不确定性。
* 信息不足、来源冲突或无法验证时，系统应明确表达未知，不用神秘分数、肯定语气或伪造依据制造确定性。
* 系统输出是供用户审视的决策信息，不是对公司、职位、用户能力或职业方向的最终裁决。
* 用户负责提供和纠正个人事实、表达目标与限制、决定是否采纳建议，并亲自完成对外沟通、投递和关键职业选择。
* AI 负责提取与追问、整理职业画像、调查与比较机会、解释证据、提出行动建议和草拟材料；AI 必须标明未知与推断，不得编造事实或擅自执行外部行动。
* 职位来源与公开信息源提供待核验的证据，不因为来自招聘平台、公司官网或搜索结果就自动成为权威事实；来源、时间、冲突和证据强弱必须保留。
* 招聘平台、模型提供商和联网服务是可替换的外部能力，受其授权、服务条款和最小必要披露约束；它们不是产品中心，也不拥有用户职业画像或最终决策权。
* 择途采用开源、自部署优先的产品模式，不把官方集中式 SaaS 作为当前或预设的商业路线。
* 用户职业画像与求职记录默认保存在用户自己控制的部署环境中，项目不依赖集中收集这些数据形成商业价值。
* BYOK 是标准能力，用户自行选择并承担模型服务；项目不以代付模型费用绑定官方托管服务。
* 项目核心优先免费使用。当前更匹配的可持续方向是个人或组织赞助，具体方案以后再验证。
* 全部核心产品能力持续开源免费，不采用通过闭源高级功能削弱社区版本完整性的 open-core 模式。
* 未来可以探索赞助、捐赠、付费支持、部署协助或咨询等收入，但收费不能成为使用完整核心能力的前提。
* 自部署模式会提高非技术用户的使用门槛，并放弃官方 SaaS 订阅等收入方式；这是已知代价，不因长期受众广泛而忽略。
* 外部模型、联网搜索和第三方服务采用最小必要披露原则，不能因为用户配置了 BYOK 就默认发送完整职业画像。
* 每项外部能力应让用户知道数据发送给谁、包含哪些类型，并允许脱敏、排除敏感内容或改用本地能力。
* 公司和职位的外部检索默认不携带可识别用户身份；只有确有必要且用户知情时，才发送与个人相关的最小上下文。
* 择途的长期产品类别是“个人职业决策系统”，不是只在找工作时使用的单点求职工具，也不扩张为管理全部日常工作的通用效率系统。
* 求职是择途落地的第一个场景；在该场景完成和验证以前，不同时铺开其他职业生涯场景。
* 求职场景的长期完整边界覆盖“认识与定位自己 -> 发现并判断机会 -> 准备申请 -> 跟踪沟通、面试与 Offer -> 记录真实结果 -> 调整策略”的决策闭环。
* 系统可以帮助用户准备材料、形成行动建议和记录结果，但不替用户自动海投、冒充用户沟通或代替用户作出关键职业决定。
* 项目发起者本人是首位参考用户，第一版必须能够及时服务其即将开始的真实求职，而不是只验证抽象概念。
* 第一阶段主要服务正在主动求职、有数年真实项目与职业积累的中文软件工程师，包括前端、后端和全栈等开发方向。
* 第一阶段目标用户描述的是产品承诺和适配优先级，不是使用准入条件；应届生、非软件职业人群和暂未求职的用户仍可使用开源产品。
* 对非目标用户，第一版不保证职业语言、招聘规则、风险信号和建议质量已经得到充分验证；系统应诚实说明当前适配范围，而不是阻止其进入产品。
* 长期目标受众是所有中文求职者，但该愿景不要求第一版理解所有行业；职业范围必须在真实使用和领域知识成熟后逐步扩展。
* 为未来扩展保留产品概念上的通用性，但不能为了提前兼容所有职业而牺牲第一阶段对软件工程师的判断深度和使用体验。
* 第一阶段的首要问题是：面对招聘平台中质量参差、信息不完整甚至失真的职位与公司，帮助用户判断一个机会是否真实、是否值得投入有限的时间精力，以及它是否符合个人职业方向。
* 第一版开始时，Agent 先通过用户基本信息、现有简历、职业材料和主动追问建立初步职业画像，并由用户确认或纠正。
* 第一版的最低启动输入是现有简历或基本工作经历，加一轮由 Agent 主导的结构化访谈；用户不需要先整理完整证据库才能开始。
* 结构化访谈重点补齐职责、项目、行动、成果、能力证据、职业目标、现实限制和不确定项，而不是让用户重复填写传统长表单。
* GitHub、项目文档、作品集、绩效材料和其他工作记录作为可选证据逐步导入，用于增强画像可信度，但不阻塞首次画像和基础简历生成。
* 系统基于已确认职业事实帮助用户生成或完善一份可用于招聘平台的基础简历，为后续职位判断和申请提供一致事实底座。
* 职业画像与能力证据是唯一职业事实源；简历是从事实源派生的表达版本，不反向成为另一套独立事实。
* 系统支持从同一职业事实源派生多个岗位定位版本，例如高级前端、前端架构或全栈；不同版本可以选择、排序和强调不同经历，但不能产生相互矛盾的事实。
* 针对具体 JD 的岗位定制简历应以某个定位版本为起点继续裁剪，而不是每次从空白重新生成。
* 职位采集支持用户主动提供的文本、链接、截图以及浏览器插件读取的当前页面；具体输入形式可分阶段实现，但不能要求用户等待平台级数据合作才能使用。
* 第一版职位输入保持来源无关，主要依靠用户主动采集；招聘平台、V2EX、掘金、公众号、公司官网、朋友内推、邮件或线下信息都可以作为来源。
* 系统分析一条机会的最低核心信息是职位描述或主要职责要求，以及公司名称；同时尽量保留职位名称、来源渠道或 URL、采集时间、地点、薪资等原始信息。
* 达到最低核心信息后即可开始分析；其他字段缺失不会阻止机会进入系统，而是由系统继续调查，并作为未知项、待确认问题或判断置信度限制明确展示。
* 所有输入保留原始内容和来源，随后由系统统一标准化并联网补充公司与职位信息。
* 公开渠道连接器是后续增强，不是第一版成立条件；每个连接器在实现前必须核验当时的服务条款、官方接口、授权范围、限流和内容权利。
* 不把绕过访问控制、反爬措施、账号限制或服务条款的大规模招聘平台爬取作为产品基础。
* 系统结合职业画像对职位进行推荐和排序，并深挖公司与岗位信息，展示来源、风险、匹配、机会成本和未知项，帮助用户决定是否值得投入。
* 机会判断必须给出明确但非强制的行动建议，例如“值得投入”“谨慎投入”或“暂不投入”，而不是只陈列信息后把全部分析工作留给用户。
* 行动建议必须同时说明关键依据、不利证据、未知项以及哪些新信息可能改变结论；用户可以质疑、覆盖或忽略建议，并保留最终决定权。
* 不以单一综合匹配分或没有解释依据的排行榜替代行动建议，也不根据建议自动执行投递或对外沟通。
* 第一版的终点是“申请就绪”：对值得申请的岗位生成基于已确认职业事实的定制申请材料和沟通草稿，交由用户审核、修改和使用。
* 第一版的“申请就绪”交付完整申请决策包，至少包含岗位定制简历、打招呼内容、应重点强调的经历、需要向招聘方确认的问题、当前未知项与风险提醒。
* 申请决策包中的每项表达应能追溯到职业画像中的已确认事实；系统可以建议如何表达，但不能补写用户没有做过的经历或成果。
* 用户亲自在 Boss 等招聘平台沟通和投递；系统不冒充用户发送消息、不自动提交申请，也不以任何形式进行自动海投。
* 自动化可以用于信息提取、联网调查、职业画像维护、机会比较、材料草拟和流程提醒，只要它不越过用户对外沟通与关键职业行动的控制权。
* 申请结果记录与策略反馈属于完整求职场景，但不是第一版达到“申请就绪”的必要终点。
* 产品是职业规划与职业决策辅助工具，不是自动投递机器；不以增加投递数量作为主要成功标准。
* 系统应结合职位描述、公司公开信息、网络检索结果、用户职业经历、能力证据、目标和现实限制提供个性化判断。
* 公司背调与职位判断必须展示信息来源、时间、证据强弱、冲突和未知项，不能把缺少依据的 AI 推断包装成事实。
* 机会判断采用“先排除硬伤和违反个人底线的机会，再对剩余机会进行个性化比较”的基本原则；具体门槛和排序规则不在当前方向讨论中展开。
* 产品的差异化价值不是单次内容生成，而是持续理解用户的事实、约束和真实职业结果，并据此支持判断与行动。
* 长期产品逐步覆盖职业生涯中的重要选择，但每条后续路线都需要基于真实需求和既有场景验证后再进入范围。
* 用户没有正在求职时，择途主要辅助职业规划：持续积累项目成果、能力证据、目标与限制的变化，并围绕明确职业目标帮助用户发现差距和准备下一步。
* 非求职阶段的能力必须与职业画像或明确职业目标直接相关；择途不接管日常待办、工时、通用知识管理或完整课程学习。
* 第一阶段必须描述一个端到端最小闭环，并说明用户在闭环前后的可观察变化。
* 必须明确产品价值观：求职者主体性、事实可追溯、AI 不编造、解释优先、隐私优先、不鼓励无差别海投。
* 必须区分长期愿景、MVP、后续能力和明确不做事项。
* 讨论中的已确认结论、未决问题和范围变化持续写入本 PRD；稳定产品事实再晋升到 `docs/product/`。
* 仓库根目录提供一个面向潜在用户和贡献者的 `README.md`，如实介绍产品愿景、原则、第一版方向、当前阶段和文档入口，不把规划中的能力描述为已经实现。

## Acceptance Criteria

* [x] 冻结产品类别：个人职业决策系统，求职是第一个场景。
* [x] 冻结核心产品承诺：提高职业决策质量与掌控感，而不是保证 Offer 或最大化投递数量。
* [x] 冻结产品中心：由 AI 协助建立的、用户拥有且持续演化的职业画像与决策记录。
* [x] 冻结画像权力关系：AI 主动理解并提出画像，用户拥有最终解释权。
* [x] 冻结 AI 顾问角色：批判性检验职业目标并提出替代路线，用户保留最终决定权。
* [x] 冻结可信判断标准：证据优先，区分事实、推断和价值判断，重要结论可追溯且允许表达未知。
* [x] 冻结部署与数据控制原则：开源、自部署优先，不做官方集中式 SaaS，用户数据保留在自己的环境中，BYOK 为标准能力。
* [x] 冻结开源能力边界：全部核心产品能力持续开源免费，不采用闭源高级功能付费墙。
* [x] 冻结外部数据边界：外部模型和联网服务遵循最小必要披露，用户可见、可控制并可选择本地替代。
* [x] 冻结第一目标用户：正在主动求职、有数年真实项目与职业积累的中文软件工程师，项目发起者是首位参考用户。
* [x] 记录长期受众：逐步扩展到所有中文求职者，但不以牺牲第一阶段深度换取名义上的通用性。
* [x] 冻结首个场景的长期边界：覆盖完整求职决策闭环，不包含替用户执行关键求职动作的自动化机器人模式。
* [x] 冻结非求职阶段边界：持续积累职业事实并围绕明确职业目标辅助规划，不扩张为日常职业生活管理工具。
* [x] 明确第一版帮助用户完成的首要结果：识别真实且值得投入的工作机会，并理解其对个人职业路径的影响。
* [x] 明确候选 MVP 的准备阶段：Agent 建立初步职业画像并帮助完善可用于招聘平台的基础简历。
* [x] 冻结第一版启动门槛：现有简历或基本经历加 AI 结构化访谈，可选证据后续补充。
* [x] 冻结简历组织方式：一份职业事实源派生多个岗位定位版本，再生成具体岗位申请版本。
* [x] 明确候选 MVP 的核心循环：采集职位、推荐与排序、调查公司和岗位、形成证据化机会判断。
* [x] 冻结第一版职位入口：主要由用户主动采集，来源无关，最低需要职位描述或主要内容与公司名称。
* [x] 冻结职位信息缺失处理：达到最低核心信息即可分析，其他缺失内容进入调查、未知项和待确认问题，不作为硬性阻塞。
* [x] 冻结机会判断表达：给出明确但非强制的行动建议，同时展示依据、未知项和可能改变结论的信息，不以黑盒分数替代判断。
* [x] 冻结 MVP 终点：机会判断后继续生成岗位定制材料和沟通草稿，达到“申请就绪”；不要求首版闭合结果反馈。
* [x] 冻结申请就绪交付物：完整申请决策包，而不是只有简历或打招呼文本。
* [x] 冻结外部行动边界：用户亲自沟通与投递，系统不自动发送、不自动提交、不自动海投。
* [x] 定义用户从进入产品到得到结果的 MVP 闭环。
* [x] 为每个 MVP 能力说明其为何是闭环必需，并将仅仅“有用”的能力延后。
* [x] 明确第一版聚焦承诺但不限制使用：优先适配有经验的中文软件工程师，不阻止其他用户使用，也不承诺未验证场景的适配质量。
* [x] 明确 AI、用户、职位数据源和平台各自承担的责任。
* [x] 确认机会判断的基本决策顺序：先排除硬伤与底线冲突，再个性化排序。
* [x] 将机会判断的具体维度、硬门槛、权重、证据要求和结果表达模板延后到独立产品任务。
* [x] 将确认后的产品边界同步到 `docs/product/`，必要的重要取舍记录到 `docs/decisions/`。
* [x] 用户最终确认文档准确表达其初衷与产品方向。
* [x] 根目录 README 如实提供项目占位介绍，并明确当前仍处于早期设计阶段。

## Definition of Done

* 当前任务 PRD 不再包含会改变产品入口或 MVP 闭环的未决问题。
* 已确认的产品前景、目标用户、首要问题、产品原则、MVP 与非目标形成公开可维护文档。
* 讨论纪要保留关键推理和被否决方案，但不直接倾倒聊天原文。
* 相关文档互相链接，后续原型和开发任务能够引用明确的产品边界。
* 本任务只完成产品定义，不以代码、测试或技术栈选择作为完成条件。

## Out of Scope

* 编写应用代码或创建前后端工程骨架。
* 选择前端、后端、数据库、模型 SDK 或部署技术栈。
* 设计完整视觉稿、页面信息架构或交互原型。

* 将旧讨论中的六页草案或任一能力地图直接视为已确认需求。
* 将自动投递、自动海投或“投得更多”作为产品核心目标。
* 在招聘平台冒充用户发送消息、自动提交申请或自动操作对外沟通。
* 第一版同时覆盖应届生和所有非软件职业人群的领域差异。
* 把目标用户聚焦实现为产品准入限制，或者阻止非目标用户使用开源产品。
* 第一版承诺已经充分适配应届生、非软件职业和非求职阶段的完整决策流程。
* 以集中托管用户职业数据的官方 SaaS 作为第一阶段或默认商业模式。
