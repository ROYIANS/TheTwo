# 探索择途系统概念 Demo

## Goal

制作一个接近成熟产品体验的择途系统概念 Demo，让用户能够直观感受“择途作为一个完整系统是什么”，并比较三种结构明显不同的产品骨架。Demo 使用虚构数据，只验证信息架构、工作入口、对象关系和视觉气质，不形成正式前端实现方案。

## Context

* 已完成的 MVP 体验主干原型验证了六阶段流程基本成立，但它仍是流程演练器，不具备完整系统概念。
* 用户希望看到一个更“高大上、精致、参考成熟产品”的系统 Demo 网页。
* 产品核心对象包括职业画像、求职方向、方向表达、机会、调查证据、机会判断和申请决策包。
* AI 必须嵌入具体任务与对象上下文，不做孤立的通用聊天首页。
* 当前没有正式前端工程、路由、组件库或 code-spec；本任务仍是独立实验原型。

## Design Question

择途采用怎样的系统级信息架构和工作台结构，才能让用户每天打开后迅速知道：

1. 现在最值得处理什么；
2. 系统掌握了哪些当前有效职业上下文；
3. 哪些机会值得投入、依据和未知项是什么；
4. 如何从机会判断进入申请准备；
5. AI 顾问如何在不夺取用户控制权的前提下持续工作。

## Requirements

* 使用一个自包含 HTML 文件，无框架、构建工具、服务器、网络请求、真实 AI 或数据持久化。
* 使用虚构的资深前端求职者“林舟”、虚构公司、职位、证据和申请材料。
* 提供三个结构明显不同的系统方案，通过 URL `?variant=A|B|C` 和固定底部切换器选择。
* 支持键盘左右方向键切换方案，不在输入控件聚焦时拦截。
* 三个方案共享同一组产品数据和核心页面，但不得只改变颜色与装饰。
* 至少提供以下可导航界面：
  * 今日 / 工作台；
  * 机会列表；
  * 单个机会的证据与判断详情；
  * 职业画像；
  * 简历与申请材料。
* 首页应优先回答“今天最值得处理什么”，而不是展示营销文案或功能介绍。
* 机会详情必须具体呈现事实、证据、推断、未知项、风险、匹配与明确建议。
* 系统建议与用户最终决定保持分离；申请材料不能隐藏风险和未知项。
* 职业画像必须体现已确认事实、AI 推断、证据和更正历史的区别。
* AI 顾问必须与当前页面或对象绑定，明确自己正在处理的上下文。
* 系统应体现自部署、个人空间、外部服务授权和数据控制，但不让设置内容抢占主要工作区。
* 界面使用成熟运营型产品的信息密度和交互层级，不制作营销 Hero、卡片瀑布、渐变背景、玻璃拟态或装饰性大图。
* 桌面和移动端均能查看核心内容并完成页面与方案切换。
* 页面明确标记为概念 Demo，不能暗示能力已经实现。

## Variants

### A：决策工作台（默认推荐）

* 左侧稳定产品导航；
* 中央以“今日决策队列”和机会对象为主；
* 右侧是随当前对象变化的 AI 顾问与上下文；
* 强调反复工作效率、任务连续性和对象关系。

### B：职业简报

* 顶部全局导航；
* 首页像一份每日职业简报，以编辑化层级组织当前方向、机会变化和关键判断；
* 进入对象后采用宽幅阅读与证据叙事；
* 强调理解、反思和掌控感，降低传统后台感。

### C：决策台账

* 紧凑命令栏与高密度表格 / 列表；
* 当前对象使用可展开检查器展示证据、风险和下一动作；
* 强调快速扫描、比较和批量审阅少量机会；
* 不引入黑盒总分或自动排名。

## Shared Demo Data

* 用户：林舟，8 年前端与全栈经历；
* 主方向：资深前端 / 前端架构；
* 并行方向：偏前端的全栈工程师；
* 当前机会：澄屿科技、岸线云、折光智能、远岚网络；
* 系统建议状态：值得投入、谨慎投入、暂不投入、等待信息；
* 待办：确认澄屿工作方式、审核岸线云定制简历、纠正一条职业画像推断；
* 当前材料：方向简历、Boss 平台档案、两个职位定制版本；
* 横切状态：事实、推断、未知项、证据来源、更正记录、系统建议和用户决定。

## Interaction

* 主导航可切换各系统界面；
* 点击机会可以进入详情；
* 首页的主要行动可以跳转到对应对象；
* 机会详情可以切换证据、匹配、申请准备等子视图；
* 方案切换保留当前系统界面，便于对照同一内容；
* 移动端使用可打开的全局导航或紧凑顶部切换，不删除核心功能。

## Acceptance Criteria

* [x] 一个 HTML 文件可以直接打开运行。
* [x] A、B、C 三个方案可通过 URL、底部切换器和键盘切换。
* [x] 三个方案在布局、信息层级和主要工作方式上结构明显不同。
* [x] 五类核心界面均可导航并呈现共享虚构数据。
* [x] 今日工作台能明确给出当前优先事项和继续工作的入口。
* [x] 机会详情可追溯展示证据、冲突、未知项、建议和用户决定。
* [x] 职业画像区分事实、推断、未知和更正记录。
* [x] 申请材料继续展示相关风险与待确认问题。
* [x] AI 顾问始终绑定当前页面或机会上下文。
* [x] 页面没有自动投递、自动沟通、黑盒总分或虚构真实能力。
* [x] 桌面、平板和手机视口没有横向溢出、文字截断或不可达核心操作。
* [x] 浏览器控制台无脚本错误。

## Design Direction

* 目标用户：正在主动求职、有多年经验、需要反复比较真实机会的中文软件工程师。
* 品牌气质：冷静、可信、锋利但不压迫；像一位有证据意识的职业顾问，而不是招聘平台或内容生成器。
* 视觉品质：成熟 B2B 产品的精确结构，加少量编辑化气质；多种中性色配合克制的绿色、铜色、蓝色和风险红。
* 核心记忆点：每个重要结论旁边都能看见依据、未知项和下一行动。
* 约束：不把所有内容装进圆角卡片，不嵌套卡片，不使用单一深蓝 / 紫色主题，不靠渐变和发光制造高级感。

## Out of Scope

* 正式 UI 规范、设计系统、组件 API、路由与工程结构；
* 真实认证、上传、搜索、OCR、模型、数据库和导出；
* 完整设置后台、管理员界面与部署流程；
* 求职申请后的面试、Offer 和结果反馈完整界面；
* 将任一方案代码直接用于正式产品。

## Decision (ADR-lite)

**Context**：单一系统稿容易过早把一种视觉结构误当成产品答案，且用户很难仅通过描述判断信息架构偏好。

**Decision**：在同一自包含 Demo 中实现三种结构差异明显的系统方案，共享同一数据和页面任务，通过固定切换器直接比较。

**Consequences**：能够更有效地选择系统骨架并组合不同方案的优点；原型代码会存在刻意重复，最终选择必须被重新设计和实现，而不是直接清理后投产。

## Validation Record

2026-08-12 使用 Playwright 与本机 Microsoft Edge 对 Demo 执行了以下验证：

* A、B、C 三个方案分别检查今日、机会列表、机会详情、职业画像、简历与材料五类界面；
* A 方案额外检查机会详情的证据与判断、个人匹配、申请准备三个子视图；
* `1440x1000`、`900x900`、`390x844` 三种视口均完成真实导航路径检查；
* 移动端导航支持打开、选择页面、点击外部关闭；
* URL `?variant=`、键盘左右切换、刷新保留方案以及切换方案后保留当前页面均通过；
* 页面没有横向溢出、按钮内容截断和浏览器脚本错误；
* 视觉复核覆盖三套桌面首页、三套移动首页，以及 A/B/C 的机会详情表现；
* 验证过程中发现并修复了 B 方案移动导航层级低于遮罩、导致无法点击的实际问题。

## Initial Comparison Notes

这些是供用户比较的观察，不是已接受的产品结论：

* **A 决策工作台**：系统对象、每日工作和 AI 上下文关系最完整，最适合成为长期使用骨架；
* **B 职业简报**：品牌人格和顾问感最强，适合首页、判断摘要和深度阅读，但日常高频操作密度较低；
* **C 决策台账**：机会扫描与证据审阅效率最高，适合机会列表和调查工作面，但整体情感温度和新用户引导最弱；
* 后续很可能不是整套选择，而是以 A 为骨架，吸收 B 的摘要表达和 C 的高密度审阅能力。是否采用该组合必须等待用户实际体验确认。
