# 定义 MVP 体验主干

## Goal

把现有产品定位和能力地图收敛为一条可讲述、可演练、可质疑的 MVP 端到端体验主干，明确用户从首次进入择途到形成申请决策包并作出申请决定的全过程。使用一次性单页概念原型辅助验证流程，但不提前固化正式界面或技术架构。

## What I Already Know

* 择途是开源、自部署、以求职者为中心的个人职业决策系统，第一个场景是求职。
* MVP 终点是“申请就绪”，不自动沟通、投递或海投。
* [产品能力地图](../../../docs/product/product-capability-map.md)已经定义能力范围、MVP 边界、横切契约和主要依赖。
* MVP 主链包括产品基础、职业事实、求职方向、方向简历、职位采集、公司与岗位调查、机会判断以及申请决策包。
* 用户建议使用若干 demo page 或单页面概念演示，使体验主干更容易理解和讨论。
* 当前仓库没有应用代码，也没有正式前端、后端或数据库 code-spec。

## Recommended Direction

制作一个可点击的单页流程原型，以连续步骤和少量关键分支演练完整体验。原型的主要问题是“流程与状态是否成立”，而不是“最终视觉风格是什么”。

原型应满足：

* 一个独立 HTML 文件即可打开，避免引入框架、依赖和正式工程结构；
* 覆盖从首次进入到用户选择申请、暂缓或放弃的完整主路径；
* 每一步展示用户目标、系统输入、AI 产出、用户确认点和被保留下来的状态；
* 至少演示信息缺失、AI 理解被用户纠正、调查证据冲突和机会不值得投入等关键分支；
* 明确标记为一次性概念原型，不作为正式 UI、组件、路由、数据结构或技术选型依据；
* 经讨论确认的结论回写 PRD 和正式产品文档，原型本身不成为权威产品规范。

## Requirements

* 定义 MVP 体验主干的阶段、顺序、进入条件和完成条件。
* 为每个阶段定义用户目标、必要输入、系统责任、用户确认点、输出、异常或未知分支、所属能力和 MVP 边界。
* 识别跨阶段持续存在的关键状态，尤其是职业事实、求职方向、证据、未知项、系统建议、用户决定和更正记录。
* 定义后续可点击单页概念原型需要演练的主路径、高价值分支和验证问题。
* 后续原型只验证体验结构和状态连续性，不评价正式视觉方案。
* 管理员邀请、部署信任说明和外部服务配置作为进入条件表达，不与个人职业建档混为同一业务阶段。
* 首次使用以形成可用职业事实底座和方向表达为阶段价值，不能要求用户先补全所有经历和证据。
* 反复使用的核心循环是“带入机会 -> 调查与判断 -> 申请准备与决定”。
* 使用完全虚构的中文资深前端求职者、公司和职位演练，不在公开原型中复制发起人的真实职业材料。

## Experience Backbone

```text
进入条件：管理员邀请、部署信任说明、外部服务配置

个人准备：
建立职业事实底座
  -> 确定求职方向与决策标准
  -> 形成可复用的方向表达

反复使用：
带入并理解一个机会
  -> 调查证据并形成机会判断
  -> 准备申请并由用户作出决定
  -> 回到下一个机会
```

六个个人体验阶段分别为：

1. **建立职业事实底座**：导入简历或基本经历，经过 AI 结构化访谈，由用户确认事实、纠正推断并保留未知项；
2. **确定求职方向与决策标准**：明确主方向、少量并行方向、可权衡偏好、现实限制和不可接受条件；
3. **形成可复用的方向表达**：从同一职业事实源派生方向定位、基础简历和招聘平台档案；
4. **带入并理解一个机会**：粘贴职位文本或上传截图，保留原始内容与来源，标准化可识别信息并暴露缺失项；
5. **调查证据并形成机会判断**：核验公司和岗位，结合用户事实与方向呈现匹配、风险、机会成本、未知项及明确但非强制的建议；
6. **准备申请并由用户作出决定**：对值得投入的机会生成完整申请决策包，由用户审核后选择申请、暂缓或放弃并记录理由。

少量机会并排比较是阶段 5 内按需触发的辅助路径，不是每个机会必须经过的独立阶段。

## Persistent Experience State

* **职业事实**：区分用户已确认事实、支持证据、AI 推断和未知项；
* **求职方向**：保存主方向、并行方向、评价标准、现实限制和生效时间；
* **方向表达**：保存方向定位版及其派生的简历和平台档案，不形成第二套事实源；
* **机会记录**：同时保存用户带入的原始内容、来源元数据、标准化信息和缺失项；
* **调查证据**：保存来源、时间、证据强弱、冲突和未知项；
* **判断快照**：分开保存系统建议、依据、不利证据、未知项和可能改变结论的信息；
* **用户决定**：保存申请、暂缓或放弃以及用户理由，不覆盖系统建议；
* **更正记录**：当前有效内容参与后续判断，被用户否定的内容不得因历史存在而重新使用。

## Prototype Scenarios

原型使用虚构用户“林舟”和虚构公司、职位，提供以下可重复演练：

1. **完整主路径**：从简历导入到一个“谨慎投入”的机会形成申请决策包；
2. **画像纠正**：AI 将“技术负责人”误解为“人员管理者”，用户纠正后下游方向表达和匹配判断同步变化；
3. **职位信息缺失**：截图缺少薪资或主体信息，系统继续分析但明确未知项和调查目标；
4. **调查证据冲突**：官网、招聘信息和弱来源评价互相冲突，系统不把单一信号升级为事实；
5. **硬约束不满足**：机会违反地点或工作方式底线，系统建议暂不投入，但用户仍保留最终决定权；
6. **按需比较**：在两个真实候选机会之间按一致维度呈现取舍，不输出黑盒总分或自动排名。

## Acceptance Criteria

* [x] 从首次进入到申请决定存在一条完整、无隐含跳步的主路径。
* [x] 每个阶段的用户目标、输入、系统责任、确认点、输出和失败分支均有记录。
* [x] 主干中的每一步都能追溯到现有产品能力地图，或明确标记为新发现的能力缺口。
* [x] 横切的事实、推断、判断、未知、证据、更正和用户最终权威在流程中有具体落点。
* [x] 已定义单页概念原型需要演练的完整主路径和至少四类高价值分支。
* [x] 已明确原型的一次性性质及结论回写规则。
* [x] 没有提前定义正式页面结构、组件系统、数据库字段、API 或应用技术栈。

## Decision (ADR-lite)

**Context**：纯文字流程难以暴露确认点、跨阶段状态和异常分支是否连贯，但当前尚未进入正式前端设计与技术选型。

**Decision**：先形成权威的 MVP 体验主干文档，再在独立 Trellis 任务和实验分支中制作一个单文件、无依赖、内存状态的可点击流程原型。原型采用连续体验阶段、可见状态和引导演练，不制作互不相干的功能页面集合。

**Consequences**：团队可以更早发现流程和状态模型的问题；原型中的页面布局、组件和代码不能直接升级为正式方案，验证结论必须回写产品文档。

## Out of Scope

* 正式产品 UI、品牌视觉和交互细节定稿；
* 前端框架、路由、组件库和工程结构选型；
* 后端、数据库、AI 编排、搜索和部署架构；
* 可复用生产代码、正式测试体系和真实数据持久化；
* MVP 之后的完整求职进程、面试、Offer 和长期职业规划流程；
* 自动获取职位页面、浏览器插件、自动沟通或自动投递。
