# ADR-0024：React 产品原型作为体验基线

## Context

产品主链已经从职业事实建立、机会材料接入、证据调查、机会判断、申请准备到用户决定收敛为一段连续体验。仅靠文字描述无法充分验证空间导航、阶段推进、证据审阅、建议质疑和最终决定之间的关系，因此需要一份可启动、可操作、可继续演进的前端原型。

## Decision

1. `prototype/` 下的纯前端 React 工程作为当前产品体验、信息架构和交互讨论的基线。
2. 后续产品讨论优先参考原型表达的三个语义域：职业事实源、研究资料库、机会研究台，以及机会研究台的五个阶段：机会档案、证据调查、机会判断、申请准备、用户决定；这些语义域不等于常驻页面菜单。
3. 当前交互基线采用无壳、对象驱动的工作台：不使用固定 header、左侧栏或常驻空间菜单；从“今天”的主任务和相关对象进入局部对象视图，深层内容提供局部返回；Agent 只保留一个绑定当前上下文的全局入口。
4. 原型中的虚构案例、内存状态、模拟解析、模拟顾问和本地反馈只用于表达体验，不代表对应的后端、模型、数据库、联网调查或第三方平台能力已经实现。
5. React、TypeScript、Vite 和原型依赖只服务于快速迭代，不构成正式生产前端、后端、数据库、模型供应商或部署技术栈决策。
6. 未来进入正式实现时，应先依据已确认的产品契约重新设计边界、数据模型和服务接口，再决定是否复用原型中的代码或迁移其交互模式。

## Consequences

正面影响：

* 产品结构不再只存在于讨论文本中，后续评审可以围绕可操作流程进行；
* 三个空间和机会研究主链成为稳定的共同语境，便于继续细化产品决策；
* 原型可以在没有真实凭据、外部服务和生产技术栈的情况下验证用户是否理解系统建议与自身决定的区别。

代价与风险：

* 原型状态不持久化，刷新后回到默认示例，不能作为真实业务数据存储；
* 原型中的视觉和组件结构可能随产品讨论变化，不能未经重新评审直接视为正式设计系统；
* 如果后续只复制原型代码而没有重新确认服务边界，可能把演示用假能力误当成生产能力。

## Alternatives Considered

### 继续只维护文字流程

维护成本较低，但难以验证连续交互、状态反馈和响应式信息优先级，未采用。

### 直接开始正式技术实现

会在产品体验尚未充分验证时锁定架构和依赖，也与当前尚未决定生产技术栈的状态冲突，未采用。

### 制作单文件 HTML 样张

可以快速展示静态视觉，但无法承载可持续演进的 React 状态和工程化交互，未采用。

## Scope Boundary

本决策只确定“以 React 工程化原型作为体验基线”，不决定：

* 正式前端框架、路由、状态管理或组件库；
* 后端语言、服务拆分、数据库、模型调用方式或联网调查实现；
* 认证、上传、持久化、导出和任何自动发送或自动投递能力。
