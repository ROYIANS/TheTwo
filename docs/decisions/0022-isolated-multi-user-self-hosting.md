# ADR-0022：首个自部署版本支持相互隔离的多个人用户

## Context

择途采用自部署模式，但“一个部署只服务一个人”与“一个部署可以服务多个彼此独立的个人”会产生不同的产品承诺。多人共用实例可以降低家庭、朋友或小型社区的部署成本，但职业画像、求职材料、模型凭据和决策记录高度敏感，不能因为共用服务器就默认互相可见。

自部署管理员实际控制服务器、数据库和备份。产品可以限制管理员在应用内的权限，却不能虚假承诺基础设施管理员绝对无法接触底层数据。

## Decision

1. 首个自部署版本支持同一实例中的多个相互隔离的个人用户。
2. 新用户只能由实例管理员邀请或创建；第一版不提供开放注册。
3. 每位用户的职业画像、职位、简历与申请材料、决策和结果记录、外部服务凭据及导出数据必须相互隔离。
4. 实例管理员在产品内默认只能管理实例和账户，不能浏览其他用户的职业内容或外部服务凭据。
5. 产品必须明确说明部署管理员在服务器、存储和备份层具有潜在数据访问能力；用户应只使用自己信任的部署实例。
6. 每位用户可以配置个人 BYOK；管理员可以提供可选的实例共享凭据，但不能强制用户使用，也不能借此获得用户内容浏览权。
7. 第一版的多用户能力只服务彼此独立的个人，不包含共享职业画像、顾问协作、团队空间、组织管理或跨用户数据分析。

## Consequences

正面影响：

* 一个自部署实例可以服务多个独立用户，降低重复部署成本；
* 产品权限明确保护个人职业数据，不把管理员身份等同于内容查看权；
* 对基础设施信任边界保持诚实，不作无法兑现的绝对保密承诺；
* 个人 BYOK 和可选共享凭据可以同时存在。

代价与风险：

* 第一版必须具备身份识别、访问控制和用户数据隔离，而不能按单用户原型设计；
* 实例管理员仍可能通过基础设施手段访问数据，部署信任无法只靠应用权限解决；
* 账户邀请、停用、删除和备份清理需要清楚的产品规则；
* 多用户能力可能被误解为团队协作，需要持续声明当前不支持共享空间。

## Alternatives Considered

### 每个实例只服务一个用户

隐私模型更简单，但多人使用时需要重复部署，也不符合已确认的首版使用方式，未采用。

### 管理员可以查看所有用户内容

管理和支持更直接，但会把高度敏感的职业数据暴露给应用管理员，与个人数据隔离原则冲突，未采用。

### 第一版包含团队协作和组织权限

可以服务职业顾问或组织场景，但会显著扩大身份、权限和共享语义，偏离个人职业决策系统的首版边界，未采用。

## Supersession

无。
