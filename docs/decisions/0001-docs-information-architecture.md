# ADR-0001：文档信息架构与治理方式

## Context

择途在进入代码设计前，需要保存产品形成过程、AI 讨论、原始需求、方案、产品和研发交付物，并以文档和 spec 驱动后续开发。

单纯按“产品输出、研发输出、运维输出”分类虽然直观，但会把原始材料、讨论稿、已接受决策和现行规范混在一起。仓库同时启用了 Trellis，如果 `docs/` 与 `.trellis/` 保存两份完整规范，也会产生双写和内容漂移。

## Decision

### 1. 生命周期优先，领域次级分类

`docs/` 顶层分为：

* `product/`：当前产品上下文；
* `specs/`：当前有效契约；
* `decisions/`：重要决策及原因；
* `work/`：讨论、提案、评估和里程碑材料；
* `evidence/`：原始需求、截图、访谈和外部参考；
* `templates/`：受治理文档的写作模板。

各目录内部再按产品、体验、AI、工程和运维等领域细分。没有正文时不创建空领域目录。

### 2. AI 讨论以结构化纪要为主

AI 讨论默认整理为背景、事实、候选方案、结论、未决事项和晋升产物。完整原文只有在具备长期证据价值、适合公开且已去除敏感信息时才保留，并且不直接构成需求或 spec。

### 3. `docs/` 是项目知识的权威正文

`.trellis/` 负责 AI 工作流状态、任务上下文、精炼执行规则和引用。长期项目知识保存在 `docs/`；Trellis 任务中的确认结论应晋升到这里，不在两处长期维护相同正文。

### 4. `docs/` 默认全部公开

少量开发期私密项目材料放在 Git 忽略的根目录 `private/`。该目录不承担产品运行时的用户数据存储职责。

### 5. 英文路径，中文正文

路径使用 ASCII 英文 `kebab-case`，正文默认中文。长期规范使用语义文件名，讨论和报告使用日期前缀，决策记录使用四位顺序编号。需要治理的 Markdown 使用轻量 YAML front matter。

### 6. 第一版采用带治理能力的最小骨架

第一版包含入口索引、当前产品摘要、两份讨论纪要、首条决策记录、截图证据以及 discussion、decision、spec 三种模板。不加入文档站、校验脚本或 CI。

## Consequences

正面影响：

* 阅读者能快速判断一份文档是当前真相、历史原因、工作过程还是原始证据；
* 项目知识不依赖 Trellis 或其他单一 AI 工具；
* 后续可以自然扩展为文档站或自动化校验；
* 现有截图中的产品、研发和运维交付物都有明确归属。

代价：

* 讨论结束后需要进行一次整理和晋升；
* 需要维护状态、相对链接和替代关系；
* 自动校验尚未建立，第一阶段依靠贡献者和 AI 遵守规则。

## Alternatives Considered

### 只按产品、研发、运维分类

容易浏览交付物，但无法表达文档生命周期和权威性，未采用。

### 只按输入、提案、决策、规范分类

生命周期清晰，但按领域查找材料的成本较高，未单独采用。

### 完整保存每次 AI 对话

追溯性最高，但噪声、重复和隐私风险过高，未采用。

### 将 `.trellis/spec/` 作为全部规范的权威来源

AI 使用方便，但普通贡献者难以发现，且项目知识依赖特定工具，未采用。

### 第一版立即加入自动检查

能提高一致性，但会过早引入脚本和 CI 维护成本，延期到文档规模增长后评估。
