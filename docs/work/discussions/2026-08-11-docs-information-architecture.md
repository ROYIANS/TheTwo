# docs 文档信息架构讨论

本文记录项目启动时对 `docs/` 结构的收敛过程，是结构化纪要，不是逐字对话。

## 目标

在不设计代码目录的前提下，先建立能够记录产品形成过程、AI 讨论、方案、原始需求和研发交付物的文档体系，并以文档和 spec 驱动后续开发。

## 输入

* 择途产品方向交接文档；
* 一张列出产品、研发和运维交付物的参考截图；
* 仓库现有 Trellis 工作流和 `.trellis/spec/`；
* 项目开源、中文优先和隐私优先的约束。

## 讨论的主要方案

### 按交付职能分类

使用产品、研发、运维、AI 等顶层目录。优点是直观，缺点是草案、当前规范和历史记录容易混在一起。

### 按文档生命周期分类

使用输入、提案、决策、规范和归档等顶层目录。权威性清楚，但按领域查找资料不够方便。

### 生命周期优先、领域次级分类

先区分产品上下文、spec、决策、工作过程和证据，再在内部按产品或工程领域细分。该方案最终被采用。

## 已确认结论

1. 顶层采用生命周期与领域结合的混合结构；
2. AI 讨论默认保存结构化纪要，完整原文按需保存；
3. `docs/` 是项目知识权威正文，`.trellis/` 是 AI 执行适配层；
4. `docs/` 默认全部适合公开，根目录 `private/` 保存少量被 Git 忽略的开发期私密材料；
5. 路径使用英文 `kebab-case`，正文默认中文；
6. 长期文档使用语义文件名，讨论使用日期，决策使用四位编号；
7. 第一版创建带治理规则和三种模板的最小骨架，不加入自动校验。

## 当前范围

第一版只创建已有正文需要的目录，并整理：

* 当前产品摘要；
* 产品方向历史交接；
* 本次文档架构讨论纪要；
* 首条文档架构决策记录；
* 参考截图证据；
* discussion、decision、spec 三种模板。
