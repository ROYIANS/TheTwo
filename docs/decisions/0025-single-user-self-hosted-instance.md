# ADR-0025：每个自部署实例只服务一个所有者

## Context

择途保存职业画像、求职限制、机会判断、申请材料和真实决定。这些内容高度个人化，产品的核心关系也是“一个人持续理解和修正自己的职业事实”，而不是多人共用一套账号与权限系统。

此前 ADR-0022 选择在同一实例中支持多个相互隔离的个人用户。该方案会把首版带入账户邀请、管理员权限、跨用户隔离、共享凭据和用户生命周期等问题，也让产品首页容易被理解为可以注册或邀请成员的自托管 SaaS。当前产品方向已经明确收窄为独立部署的个人系统，因此需要重新确定实例与使用者的关系。

## Decision

1. 每个择途部署实例只服务一个人，并且只存在一个所有者账户。
2. 产品不提供公开注册、成员邀请、账号切换、组织、角色或多个个人账户的数据隔离能力。
3. 单用户不等于无认证。正式实现仍需保护所有者入口，并依据部署环境设计会话、凭据和恢复机制。
4. 职业事实、机会、材料、建议、决定、外部服务凭据、导出和删除都属于该实例的唯一所有者，不建立多人共享或跨用户可见性语义。
5. 所有者自行配置 BYOK 或本地模型等外部能力；产品不提供实例管理员向多个用户分发共享凭据的机制。
6. 数据默认保存在所有者控制的实例中。若所有者委托他人维护服务器、存储或备份，产品必须诚实说明维护者在基础设施层可能接触数据。
7. 多个人希望使用择途时，应各自部署独立实例。官方集中式多租户 SaaS 仍不属于当前产品路线。

## Consequences

正面影响：

* 首页、首次进入和设置可以围绕唯一所有者设计，不再暗示注册、邀请或团队能力；
* 身份、权限和数据模型可以删除多用户隔离、管理员后台和账户生命周期等非核心复杂度；
* 职业数据归属更直接，产品叙事与“个人职业决策系统”保持一致；
* BYOK、导出、备份和删除都可以按实例所有者定义清晰边界。

代价与风险：

* 家庭、朋友或小型社区不能共用一个实例，必须承担多个部署的资源和维护成本；
* 正式实现仍需认证、备份安全和部署信任说明，不能因为只有一个用户就忽略访问保护；
* 如果未来重新考虑多人托管，需要新的产品决策和独立架构设计，不能在当前单用户模型上悄悄增加账户表和邀请入口。

## Alternatives Considered

### 同一实例支持多个隔离用户

可以降低重复部署成本，但会显著扩大身份、权限、隔离、管理员和共享凭据的产品边界。它已不符合当前“每个实例服务一个人”的明确方向，因此取代 ADR-0022。

### 单用户实例完全不设认证

局域网内使用更简单，但部署暴露、共享设备和远程访问都可能泄露高度敏感的职业信息。单用户只收窄账户数量，不取消入口保护。

### 官方提供多租户 SaaS

可以降低部署门槛，但会改变数据控制、运维责任和商业路线，不属于当前或预设方向。
